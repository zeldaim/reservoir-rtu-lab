## 1. 기획 의도

### 1.1 문제
- 배수지 · 가압장 같은 소규모 수도 시설은 대부분 **무인**으로 운영되고, 현장 장치(RTU)가 수위를 재고 밸브 · 펌프를 원격으로 제어한다.
- 이 장치는 두 방향으로 공격받는다.
  - **물리 침입:** 사람이 없는 시설에 들어와 장치를 조작한다.
  - **사이버 조작:** 원격 접속으로 설정값 · 명령을 바꾼다. 실제 사례: 2021년 미국 플로리다 올즈마(Oldsmar) 정수장 — 원격 접속으로 수산화나트륨 투입량을 약 100배로 바꾸려 한 사건 (운전원이 화면에서 보고 되돌림). 단, 2023년 당시 시 관계자가 외부 해킹이 아니라 직원 실수였을 가능성을 언급한 바 있어, 문서에는 "보고된 사건"으로 인용하고 출처를 단다.
- 수도 시설은 주요정보통신기반시설로 관리되는 대상이라, 장치 단계의 보안이 중요하다.

### 1.2 목표
수업에서 배운 부품만으로 **출입통제 + 공정 제어 + 보안 감시**를 하는 RTU 프로토타입을 만들고, 공격을 재현해 방어가 실제로 동작하는지 **측정**한다.

### 1.3 생성형 AI 활용
- 장치가 남긴 사건 기록(침입 · 잠금 · 공정 경보)을 관제 서버가 모아 **생성형 AI 로 한국어 사고 리포트**를 만든다 — 운전원이 로그 수십 줄 대신 "무엇이 · 언제 · 얼마나 위험한지 · 무엇을 할지"를 읽게.
- AI API 키는 **서버에만** 둔다 (현장 장치는 분해되면 키가 털린다).

## 3. 구현 과정

> 단계마다: 무엇을 · 왜 · 어떻게 · **결과(측정값 · 캡처)** · 겪은 문제

### 3.1 단계 1 — 출입통제 (`firmware/doorlock`)
- (채울 것) Wokwi 실행 캡처, 잠금 동작 시리얼 로그

### 3.2 단계 2 — RTU + FreeRTOS (`firmware/rtu`)
- 왜: 단일 `loop()` 구조에서는 통신(1~3초) 동안 수위 제어까지 멈춘다 → 물이 넘쳐도 밸브를 못 연다.
- 어떻게: 공정(우선순위 4) · 입력(3) · 소리(3) · 침입(2) · 전송(1) · 콘솔(1) 작업으로 나누고, 큐 · 뮤텍스로 연결.
- 결과 (채울 것 — Wokwi `stat` 출력):

| 구조 | 공정 작업 최대 간격 | 입력 작업 최대 간격 |
|---|---|---|
| 단일 구조 (`NET_IN_LOOP 1`) | ? ms | ? ms |
| 작업 분리 (`NET_IN_LOOP 0`) | ? ms | ? ms |

### 3.2.1 겪은 문제 — 온습도 센서가 제어를 멈춤 (Wokwi 실측)
- 처음에는 DHT 를 침입 감지 작업(코어 1)에서 읽었다. 결과: 읽기가 8초마다 실패(`SENSOR_ERR`)하고, `stat` 의 최대 간격이 **공정 0.41초(원래 0.2초 주기) · 입력 0.16초(원래 0.005초)**.
- 원인: DHT 는 마이크로초 타이밍으로 읽어서 라이브러리가 읽는 동안 인터럽트를 막는다 → 같은 코어의 다른 작업이 멈추고, 다른 일이 끼어들면 읽기가 깨진다.
- 해결: DHT 를 제어 작업이 없는 **코어 0** 의 따로 작업으로 옮기고, 실패는 3번 연속일 때만 기록 · 회복도 기록.
- 결과 (Wokwi `stat`, 사건 없는 10초 구간):

| | 공정 작업 최대 간격 | 입력 작업 최대 간격 | DHT 읽기 실패 |
|---|---|---|---|
| 고치기 전 (DHT 코어 1) | 374~450 ms | 120~197 ms | 8초마다 |
| 고친 뒤 (DHT 코어 0) | 256 ms | 11~12 ms | 0 (8분 동안) |

- 고치기 전 기록 중 DHT 가 우연히 안 실패한 10초 구간 하나는 입력 간격이 11.2 ms 였다 — DHT 가 원인이라는 증거.
- 배운 것: 실시간 제어 장치에서는 "무엇을 읽느냐"보다 **어디서(어느 코어 · 어느 작업에서) 읽느냐**가 제어 지연을 정한다.

### 3.2.2 겪은 문제 — 사건 폭주 · 경보 떨림 (Wokwi 실측)
- 수위 슬라이더를 빠르게 끌자 몇 초 안에 `LEVEL_JUMP` 수십 건 → 전송 큐(20칸)가 가득 차 `WARN 사건 큐가 가득 참` — **다른 중요한 사건까지 전송을 못 했다**. 실제 관제에서 사고 하나가 경보 수백 건을 만들어 진짜 경보를 묻는 것과 같은 문제.
  - 해결: 첫 급변만 바로 기록, 이후 10초는 세기만 하다가 "+N건 · 최대 속도" 한 줄로 묶음 (경보 묶음 · throttle).
- 수위가 190cm 언저리에서 오르내리자 넘침 경보(HH)가 거듭 울렸다 (경계에서 떨림).
  - 해결: 경보 해제는 기준에서 5cm 되돌아와야 (히스테리시스).
- 공정 작업 주기가 200 ms 가 아니라 256~261 ms. 처음엔 LCD(I2C)를 0.2초마다 다시 써서라고 짐작해 바뀔 때만 쓰게 고쳤지만 **그대로 261 ms** — 짐작이 틀렸다.
  - 진짜 원인: `vTaskDelay(200)` 은 "일한 뒤 200 ms 쉼"이라 주기 = 200 + 일한 시간(약 60 ms). 실시간 제어에는 `vTaskDelayUntil`(지난번 깨어난 때부터 200 ms — 고정 주기)을 써야 한다 → 바꿈. **고친 뒤 `process=200.0` ms** (9번 연속 200~202).
- 모터 온도(가변저항)를 손으로 돌리자 1초 안에 14 → 317 → 14°C — 인터록은 맞게 켜졌다 꺼졌지만, 실제 모터는 이렇게 못 변한다 → 개선 방향: 수위 급변처럼 **온도 변화 속도로 센서 이상 · 조작 의심** 판정.
- 확인한 동작: 모터 70°C↑ 인터록(펌프 강제 정지) · 60°C↓ 해제, 설비실 44.8°C `ENV_HOT` · 91% `ENV_HUMID`, `log` 명령으로 사건 20건 순서대로, PIN 열림 · 5초 뒤 자동 잠금, 5번 틀림 → 30초 잠금 → 해제, **인증 없는 움직임 = `INTRUSION` · PIN 뒤 60초 안 움직임 = `MOTION`(정상 출입)**, 수위에 따른 밸브 · 펌프 전환, 고갈 · 넘침 경보.

### 3.3 단계 3 — 장치 → 관제 서버 전송 (Wokwi 실측, 2026-11-23)
- 무엇을: 사건을 묶어(최대 10건) 서명해서 서버로 보냄. 장치 토큰(누구) + HMAC-SHA256 서명(내용 · 시각 · 일련번호가 그대로인지) + 시각 ±300초 + 계속 커지는 일련번호(같은 요청 다시 보내기 차단). 비밀값은 서명에만 쓰고 보내지 않음.
- 경로: Wokwi(ESP32) → Wokwi 게이트웨이 → 인터넷 → Cloudflare 임시 터널 → nginx(레이트 리밋) → 관제 서버
- 서버 쪽 확인: 가짜 장치로 정상 묶음 200 · 같은 번호 다시 보내기 409(`replayed_seq`)

#### 3.3.1 겪은 문제 — 연결이 안 됨, 원인을 하나씩 좁힘
| 증상 (시리얼) | 원인 | 조치 |
|---|---|---|
| `status=-100`, 0ms | `SERVER_URL` 앞뒤 공백 — 주소로 인식 안 됨 | 주소 앞뒤 공백 · 끝 `/` 자동 정리 |
| `wifi 연결 실패` | Wokwi Wi-Fi 가 10초 안에 안 붙음 + 다시 시도마다 `WiFi.begin` 을 새로 불러 연결이 처음부터 다시 시작 | `begin` 한 번 + 자동 재연결, Wokwi-GUEST 채널 6, 20초 대기 |
| `status=-1`, 17초, `tls=-29312 (EOF)` | TLS 도중 **서버(Cloudflare) 쪽이 끊음**. 인증서 묶음은 PC 에서 확인하면 정상 → 시간 문제로 추정 | 진단 스위치로 인증서 확인을 잠깐 끄니 **약 8초에 200** → 원인 = 인증서 체인 확인 시간 |
| (위 원인) | 체인: 서버 인증서 ← 중간 WE1(P-384 서명) ← GTS Root R4. 시뮬레이터에서 P-384 검증이 특히 느림 | **중간 인증서 WE1 을 신뢰 목록 앞에** 넣음(GTS Root R4 서명 확인 후) — 확인은 켠 채로 무거운 단계만 건너뜀. 확인 켠 상태로 200(12.3초) |
| 첫 시도가 11초에 끊기기도 함 | 핸드셰이크 11~12초 ↔ Cloudflare 약 17초 — 한계에 걸침 | **연결 재사용(keep-alive)** + 사건 없을 때 30초마다 `/healthz` 로 연결 유지 |

- 결과 (Wokwi `NET` · `STAT`):

| 전송 | 걸린 시간 | 연결 |
|---|---|---|
| 첫 전송 (3건) | 13,006 ms | 새 연결 (TLS 핸드셰이크 포함) |
| 다음 전송 (3건) | **795 ms** | 연결 재사용 |

  - `net_conn_new=1`(연결 한 번만) · `net_fail=0`. 전송하는 동안에도 공정 제어 주기 `process=200.0 ms` 그대로 — 2단계에서 통신을 별도 작업으로 나눈 효과.
- 배운 것: 오류 번호를 그대로 읽어야 원인이 좁혀진다(`-29312` = 상대가 끊음 ≠ 인증서 거부). 진단으로 보안 기능(인증서 확인)을 껐다면 원인을 찾은 뒤 반드시 되돌리고, 끈 채로 둔 대신 무엇으로 해결했는지 기록한다.
